# P0 — Ship blockers

## 1. Web bundle does not build

`npx expo export -p web` fails after ~139s:

```
Web Bundling failed 139016ms node_modules/expo-router/entry.js (2817 modules)
SyntaxError: app/story/view/[userId].tsx: Identifier 'nextStory' has already been declared. (136:8)
```

`nextStory` and `prevStory` are each declared twice in
`apps/expo/app/story/view/[userId].tsx` — once around lines 100-101 and again at
line 136. This is a Babel-level parse error, so the **native build fails at the
same point**; it is not web-specific.

`tsc` also reports it (`TS2451: Cannot redeclare block-scoped variable`) at lines
100, 101 and 136.

**Fix:** delete the duplicate declarations, keeping the `useCallback` versions.

## 2. Stories feature is completely dead

`apps/expo/src/services/stories/storyService.ts` calls six functions that it never
imports:

- `getUserStoriesLocally`
- `saveUserStoriesLocally`
- `markStoryAsSeenLocally`
- `reactToStoryLocally`
- `queuePendingAction`
- `checkAndSync`

All six **are** correctly exported from
`apps/expo/src/services/stories/offlineStoryService.ts` — the import statement is
simply missing. Every call is a `ReferenceError` at runtime.

The error cannot be swallowed either, because `fetchStories()`'s catch block calls
one of the same broken functions:

```ts
// storyService.ts:38-42
} catch (error) {
  console.error("[fetchStories] error:", error);
  return await getUserStoriesLocally();   // line 41 — throws again
}
```

So `fetchStories()` throws whether `forceRefresh` is true or false.

**Fix:** add the missing import from `./offlineStoryService`.

## 3. WatermelonDB decorators are not enabled anywhere

The models in `apps/expo/src/database/models/` use `@field(...)` / `@date(...)` /
`@readonly`, but:

- `apps/expo/tsconfig.json` does not set `experimentalDecorators`
- `apps/expo/babel.config.js` has only `babel-preset-expo` and `module-resolver`
  — no `@babel/plugin-proposal-decorators`

This is not just a type-check complaint: without the Babel plugin the decorators do
not work at runtime either. And `apps/expo/app/_layout.tsx:33` has

```ts
import '@/src/database'; // Initialize WatermelonDB
```

at the app root, so this module loads on **every** app start.

Two further problems in the same layer:

- `StoryModel.ts:2` imports `boolean` from `@nozbe/watermelondb/decorators`, which
  does not export it
- `StoryModel.ts:7-8` applies `@field('id')` to `id`, which collides with the
  inherited accessor on `Model` (`TS2610`)

**Fix:** enable decorators in both configs, drop the `boolean` import, and remove the
`@field('id')` override. Then re-run typecheck — the remaining model errors are
downstream of these.

# P0 — Security

Three chat authorization checks are missing. Note that the WebSocket path
(`apps/worker/src/index.ts:174-181`) does this correctly:

```sql
SELECT 1 FROM chats WHERE id = ?
  AND EXISTS (SELECT 1 FROM json_each(chats.users) WHERE json_each.value = ?)
```

The REST paths were never given the same check. That query is the fix for all
three findings below.

## 5. `deleteChat` — any user can delete any chat

`apps/worker/src/routes/api.ts:1166-1172`

```ts
case "deleteChat": {
  const { chatId } = body;
  if (!chatId) throw httpsError("invalid-argument", "chatId is required.");
  await db.delete(schema.messages).where(eq(schema.messages.chatId, chatId));
  await db.delete(schema.chats).where(eq(schema.chats.id, chatId));
  return c.json({ success: true });
}
```

Only a `chatId` is needed. Membership is never checked. Destructive and
irreversible — it deletes the chat and every message in it.

## 6. `sendMessage` — any user can inject into any chat

`apps/worker/src/routes/api.ts:1141-1155`

No membership check. The message is inserted, the chat's `lastMessage` is updated,
and the event is published to the realtime channel. This action also has **no rate
limit**, unlike likes (`120/60s`) and comments (`30/60s`).

## 7. `GET /read/chats/:id/messages` — any user can read any DM

`apps/worker/src/routes/read.ts:1209-1221`

`requireAuth` only proves *someone* is logged in. Chat membership is not verified,
so any authenticated user who has a chat id can read the whole conversation
(200 messages per call).

## 8. `GET /read/stories/:id/viewers` — story owner not checked

`apps/worker/src/routes/read.ts:1400-1419`

Any authenticated user can see who viewed anyone else's story, including each
viewer's reaction. Should be restricted to the story's owner.

## 9. `GET /read/users/:id/bookmarks` — IDOR

`apps/worker/src/routes/read.ts:1060-1072`

The `:id` path param is used directly in the query and never compared against
`c.get("user").uid`, so any authenticated user can read anyone's saved posts.

Compare with the correct pattern used by `/read/deposits`, `/read/withdrawals` and
`/read/transactions`, which all derive the uid from the token:

```ts
const uid = c.get("user").uid;
```

# P1 — Money correctness

## 10. Withdrawal state machine has no atomic guard

`apps/worker/src/routes/admin.ts:2015-2071`

Two distinct bugs in one handler.

**Double refund.** The handler reads `w.status` via a `SELECT` at line 2021, decides
whether to refund based on that value, then writes the new status unconditionally at
line 2062. There is no compare-and-swap between the read and the write. Two
concurrent `reject` calls — or a double-click on Reject in the admin panel — both
observe `status === "pending"` and **both issue a refund**.

**Invalid transitions are allowed.** Nothing validates the status transition. For a
`reserved` row you can call `reject` (coins are refunded) and then call `paid` — the
`w.reserved` branch performs no deduction, so the row is simply marked `paid`. Net
result: the user keeps their coins **and** the payout goes out.

The correct pattern already exists in this codebase —
`apps/worker/src/lib/coinOrders.ts:86-92`:

```ts
const claim = await db
  .update(schema.paymentOrders)
  .set({ status: "paid", paymentId, source, creditedAt: ts, updatedAt: ts })
  .where(and(eq(schema.paymentOrders.orderId, orderId),
             ne(schema.paymentOrders.status, "paid")))
  .run();
if (claim.meta.changes === 0)
  return { credited: false, reason: "already", coins, uid: order.userId };
```

**Fix:** claim the withdrawal row with the same conditional update + `changes === 0`
check, and add an explicit allowed-transition table
(`pending → approved|rejected`, `approved → paid|rejected`, `paid → ∅`,
`rejected → ∅`).

## 11. No idempotency layer on `/admin`

`enforceIdempotency` is wired into `/api` only (`apps/worker/src/routes/api.ts:124`).
The admin money actions — withdrawals, deposits, wallet adjustments — have no
equivalent protection.

# P1 — Config and ops gaps

## 12. `ALLOWED_ORIGINS = "*"` in production

`apps/worker/wrangler.toml`, `[vars]`. Wide-open CORS on an API that handles wallets,
deposits and withdrawals. Pin it to the app and admin origins.

## 13. `.dev.vars.example` is missing the payment secrets

The file lists `FIREBASE_SERVICE_ACCOUNT`, `R2_*`, `TWILIO_*`, `RESEND_API_KEY`,
`EMAIL_FROM` and `ADMIN_PROXY_SECRET` — but **not** `RAZORPAY_KEY_SECRET` or
`RAZORPAY_WEBHOOK_SECRET`.

The code is correctly fail-closed on both, which means a fresh production setup will
silently reject all top-ups (and return `503 not_configured` from the webhook) with
no obvious clue as to why.

## 14. `apps/worker/README.md` documents things that do not exist

- It says `.github/workflows/worker-production.yml` applies migrations and deploys on
  every push to `main`. **That file does not exist** — `.github/workflows/` contains
  only `ci.yml`.
- It says a `predeploy` script applies remote migrations and a `predev` script applies
  local ones. **Neither script exists** in `apps/worker/package.json`.

The actual mechanism is the runtime auto-migrator (`src/db/autoMigrate.ts`), which
does work. But there is no automated deploy pipeline at all — deploys are manual.

## 15. `autoMigrate` has no distributed lock

`apps/worker/src/db/autoMigrate.ts` guards against re-running per isolate, but the
`d1_migrations` row is only inserted **after every statement in the file has run**
(line 64). Multiple isolates across colos can therefore run the same migration
concurrently.

DDL is mostly tolerable because `isIgnorable()` swallows `duplicate column name` and
`already exists`. But `migrations/0012_auth_unique_identifiers.sql` contains data
statements:

```sql
UPDATE users SET email = lower(email) WHERE email IS NOT NULL AND email <> lower(email);
```

These particular UPDATEs are idempotent, so nothing is broken today. Any future
non-idempotent backfill would be applied more than once.

**Recommendation:** keep migrations DDL-only and idempotent. Run data backfills as
explicit one-shot admin actions instead.

## 16. `splitStatements` is a naive `;` split

`apps/worker/src/db/autoMigrate.ts:18-30` strips `--` comments and splits on `;`.
This breaks on `CREATE TRIGGER ... BEGIN ... END;` and on any `;` inside a string
literal. No migration currently contains either, so this is a latent trap rather
than a live bug.

## 17. Smaller items

- `ADMIN_PROXY_SECRET` is compared with `===` (`apps/worker/src/routes/admin.ts:120`),
  not a timing-safe comparison. The codebase already has `timingSafeEqualHex` in
  `lib/payments.ts`.
- `requireAdmin` in `apps/worker/src/middleware/auth.ts:69` is dead code (zero
  callers — `/admin` has its own gate), and unlike the other middleware it does not
  call `assertAccountNotBlocked`.
- Vote dedup uses a client-supplied `deviceId` (`api.ts:406`), which an attacker can
  rotate. Partially mitigated by the per-IP cap.
- `functions.tar.gz` is 19 MB of dead Firebase Cloud Functions committed at the repo
  root, and the root `package.json` still has `functions:serve` / `functions:build` /
  `functions:deploy` scripts that `cd functions` — a directory that does not exist.
- `rateLimit` fails open on KV errors and KV is eventually consistent, so limits are
  approximate. This is a documented, deliberate trade-off.

# What is already solid

Worth stating plainly, because the payment layer is genuinely well built and should
not be "fixed":

- **Razorpay signature verification is correct in both schemes.** Checkout uses
  `HMAC-SHA256(order_id|payment_id)`; the webhook signs the **raw body**, and
  `routes/webhook.ts:24` reads `c.req.text()` before any parsing. Both are
  fail-closed when the secret is absent, and both use a timing-safe hex compare.
- **Coin crediting is exactly-once** via a status CAS on `payment_orders`, with the
  `payments` insert (PK = `paymentId`, `onConflictDoNothing`) as a second guard.
- **Withdrawals escrow at request time** with a conditional `WHERE dpcoin >= amt`
  plus an affected-row check, closing the request-then-spend race.
- **Voting is well hardened:** self-votes blocked, vote target validated as a
  participant, per-user and per-IP velocity caps, expiry enforced exactly at
  `expiresAt`, and dedup by both uid and deviceId inside a per-match Durable Object
  that keeps the hot path off D1's single writer.
- **Blocked accounts are revoked immediately** — D1 is checked on every request
  rather than trusting the ID token's hour-long validity, and existing WebSocket
  sessions are closed through the Durable Object.
- **Admin audit log**, D1 error logs with retention pruning, security headers, and
  request-id correlation are all in place.
- **No secrets leak into the admin bundle.** The panel authenticates with Firebase ID
  tokens; `X-Admin-Secret` appears nowhere in `apps/admin-panel/src`.
